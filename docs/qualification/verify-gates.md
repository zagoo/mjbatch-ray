# `[VERIFY]` release gates

The design defines `[VERIFY]` items as "release gates with a specified verification
method, never permission to silently assume" (design line 36). It lists them at line
1188 and states two of them inline, at line 321 (query/warmstart) and line 1038
(CPU Manager and NUMA admission). This register enumerates every item: how it is
enforced, how it was verified, the status (same four statuses as the
[requirement matrix](requirements.md)), and what is left.

| ID | Gate (design line) | Enforcement / method | Status | Evidence | Remaining |
|---|---|---|---|---|---|
| V-1 | Exact Ray / KubeRay / MuJoCo / MJBatch image compatibility (1188); parity rerun against the exact MuJoCo 3.13.0 tree (36) | Every process runs the version check and the MJBatch behavior probes (`check_environment`); `raysimbatch.cli compat` runs in the image; rendered RayClusters are validated against the KubeRay 1.7.0 CRD; parity tests run against the MuJoCo 3.13.0 wheel | **VERIFIED** (arm64 CPU image; amd64 CPU image under emulation) | `tests/deployment/test_render.py`; smoke reports (`compat` section) in `evidence/deploy/`; `evidence/tests/parity-100k.log`; `tests/upstream`; `evidence/deploy/amd64-image/runtime-checks.txt` | The amd64 image on x86-64 hardware with Ray running (Ray does not stay up under emulation): **BLOCKED** (R-X86). Each gate's failure behavior follows the design. A failing probe or version check stops
the process before it does any work (V-1). A node refused by admission fails its
workers' start loudly (V-2). A failed pin makes worker construction fail (V-3).
